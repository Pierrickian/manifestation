# Protocole Diagnose v1

## Statut et lien runtime

Ce protocole décrit le diagnostic d’un échange Creatia runtime ou d’une application générée compatible Creatia. Les champs de diagnostics host/iframe et les messages observables sont définis dans [`runtime-api/creatia-runtime/v1`](../../runtime-api/creatia-runtime/v1/). Ce document se limite au processus de diagnostic.

## Acteurs

- **Diagnostiqueur Creatia** : capacité système chargée d’identifier les incompatibilités, ruptures de contrat et blocages runtime.
- **Creatia host** : fournit traces, réponses brutes normalisées, validation et état de bridge.
- **Application générée** : expose ses comportements observables, son application de payload et ses erreurs UI.
- **IA runtime** : peut être la source d’une réponse non conforme ou insuffisamment projetable.
- **Opérateur ou agent** : consulte le diagnostic et décide d’une réparation ou d’une évolution documentaire.

## Séquence

1. Collecter le contexte d’échec : action utilisateur, trace, statut, logs host, diagnostics iframe et réponse IA normalisée si disponible.
2. Identifier l’étape fautive : bridge, demande, prompt runtime, appel IA, validation host, transport du résultat ou application du payload.
3. Comparer les observations au contrat `creatia-runtime/v1` sans inventer de nouvelle shape locale.
4. Classer l’écart : indisponibilité, concurrence, timeout, réponse IA invalide, payload absent, application non compatible ou rendu non projetable.
5. Produire un diagnostic actionnable avec cause probable, preuves et prochaine action recommandée.
6. Si la cause implique une réparation, transmettre le diagnostic au protocole Repair v1.

## Responsabilités

### Diagnostiqueur Creatia

- Distinguer symptôme utilisateur, cause runtime et responsabilité propriétaire.
- Vérifier d’abord le chemin validé `runtimePayload` avant d’envisager un remplacement HTML complet.
- Ne pas masquer un mismatch de contrat derrière un fallback silencieux.
- Formuler des recommandations limitées à la couche responsable.

### Creatia host

- Rendre les étapes runtime observables par des logs et diagnostics.
- Conserver les informations nécessaires à la validation du résultat IA.
- Signaler explicitement les erreurs de contrat.

### Application générée

- Fournir des états UI récupérables et des traces utiles quand elle émet une intention.
- Éviter les stubs locaux qui faussent le diagnostic du bridge.
- Ne pas présenter un payload brut comme preuve de fonctionnement utilisateur.

## Entrées / sorties

### Entrées

- Trace ou identifiants de requête.
- Logs host et événements iframe disponibles.
- Statut runtime observé.
- Réponse IA brute ou structurée si disponible.
- Description de l’action utilisateur et de l’état applicatif au moment de l’échec.

### Sorties

- Classement de l’échec.
- Cause probable et composant responsable.
- Preuves observables : étapes, statuts, diagnostics, réponse manquante ou payload non applicable.
- Recommandation : réessai, réparation applicative, correction prompt, correction host ou mise à jour de documentation/tests si le contrat évolue.

## Erreurs

- **Diagnostic incomplet** : signaler les preuves manquantes plutôt que conclure définitivement.
- **Contrat divergent** : renvoyer vers `runtime-api/creatia-runtime/v1` et demander une correction alignée ou une nouvelle version si le changement est cassant.
- **Fallback trompeur** : noter que le fallback protège l’expérience mais ne prouve pas la compatibilité applicative.
- **Cause multiple** : lister les causes dans l’ordre du flux runtime pour éviter de réparer la mauvaise couche.

# Protocole Runtime Generation v1

## Statut et lien runtime

Ce protocole décrit la génération runtime après réception d’une intention applicative. Les enveloppes, statuts et champs projetables normatifs restent définis par [`runtime-api/creatia-runtime/v1`](../../runtime-api/creatia-runtime/v1/). Ce document décrit le déroulé et les responsabilités sans dupliquer les shapes.

## Acteurs

- **Application générée** : émet une demande runtime depuis l’iframe.
- **Creatia host** : transforme la demande en appel IA runtime, valide le résultat et répond à l’iframe.
- **Prompt assembly / orchestration IA** : construit l’instruction runtime à partir du contexte Creatia et du contrat attendu.
- **IA runtime** : produit la réponse `runtime_generation`.

## Séquence

1. L’application générée appelle le bridge avec une demande runtime sérialisable.
2. Le guard/bridge iframe ajoute les métadonnées nécessaires, notamment les identifiants de requête ou de trace quand ils manquent.
3. Creatia host reçoit le message runtime et classe le déclencheur.
4. Creatia host construit le prompt runtime en intégrant le contexte utile, le contrat `runtime_generation` et les contraintes de projection `runtimePayload`.
5. Creatia host appelle l’IA runtime.
6. Creatia host normalise la réponse brute, extrait le résultat structuré et vérifie qu’un payload consommable existe.
7. Creatia host renvoie à l’iframe un résultat de succès ou d’erreur conforme au contrat v1.
8. L’application générée applique le payload ou traite l’erreur de manière uniforme.

## Responsabilités

### Application générée

- Envoyer un état utile, minimal et sérialisable.
- Émettre une intention claire plutôt qu’une demande de persistance ou de secret.
- Consommer le résultat via le mécanisme runtime prévu par l’API v1.

### Creatia host

- Construire le prompt réel envoyé à l’IA runtime.
- Protéger la frontière host/iframe : concurrence, timeout, indisponibilité, validation.
- Normaliser les alias et diagnostics attendus par les consommateurs existants.
- Ne pas retourner un succès si aucun contenu projetable ou patch utile n’est disponible.

### IA runtime

- Répondre dans le type attendu par la génération runtime.
- Privilégier des évolutions applicatives applicables : patch d’état, contenu visible, choix, items, fragments ou écran suivant.
- Éviter le remplacement HTML complet comme chemin par défaut de v1.

## Entrées / sorties

### Entrées

- Demande runtime issue de l’application générée.
- Contexte projet et continuation disponibles côté Creatia.
- Instructions de prompt alignées avec `creatia-runtime/v1`.

### Sorties

- Réponse runtime host/iframe avec statut explicite.
- Payload runtime projetable ou erreur runtime normalisée.
- Diagnostics de validation et journalisation de progression côté host.

## Erreurs

- **Demande invalide ou non sérialisable** : le host doit produire un résultat d’erreur diagnostiqué.
- **Provider IA indisponible** : la réponse doit permettre à l’application générée de sortir du chargement.
- **Réponse brute non structurée** : le host doit conserver les diagnostics et éviter un succès trompeur.
- **Absence de `runtimePayload` utile** : le host doit traiter la réponse comme une erreur de contrat.
- **Échec d’application côté iframe** : l’application doit préserver l’état utilisateur exploitable et exposer une reprise.

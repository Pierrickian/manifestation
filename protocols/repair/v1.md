# Protocole Repair v1

## Statut et lien runtime

Ce protocole décrit la réparation d’une application générée, d’un prompt runtime ou d’un échange Creatia non conforme. Les contrats normatifs, messages et payloads restent ceux de [`runtime-api/creatia-runtime/v1`](../../runtime-api/creatia-runtime/v1/). La réparation doit préserver le chemin validé `runtimePayload`.

## Acteurs

- **Réparateur Creatia** : capacité système qui propose ou applique une correction ciblée.
- **Diagnostiqueur Creatia** : fournit la cause probable, les preuves et le composant responsable.
- **Creatia host** : applique les corrections host, prompt ou validation lorsque la responsabilité lui appartient.
- **Application générée** : reçoit les corrections de compatibilité, d’appel bridge ou d’application de payload.
- **IA runtime** : peut être réorientée par un prompt ou une contrainte de sortie corrigée.
- **Opérateur ou agent** : valide les changements et vérifie les tests ou checks pertinents.

## Séquence

1. Partir d’un diagnostic explicite plutôt que d’une intuition de refactor.
2. Déterminer la couche responsable : application générée, prompt assembly, host runtime, validation, documentation ou test.
3. Choisir la plus petite correction qui restaure le contrat v1.
4. Préserver les chemins validés : bridge host, demande runtime, réponse `runtime_generation`, `runtimePayload` et application visible du payload.
5. Appliquer la correction en évitant les stubs, simulations locales ou déplacements de responsabilité.
6. Vérifier que l’erreur initiale disparaît et que les états d’échec restent récupérables.
7. Mettre à jour la documentation, les prompts ou les tests seulement si la correction formalise une nouvelle règle ou clarifie le contrat existant.

## Responsabilités

### Réparateur Creatia

- Réparer la cause identifiée sans introduire de protocole parallèle.
- Maintenir l’alignement avec `creatia-runtime/v1`.
- Refuser les corrections qui déplacent secrets, persistance ou orchestration IA vers l’application générée.
- Documenter toute clarification durable dans la couche appropriée.

### Creatia host

- Corriger les erreurs de bridge, orchestration, timeout, validation ou diagnostic qui lui appartiennent.
- Continuer à renvoyer des erreurs normalisées permettant à l’iframe de sortir du chargement.
- Ne pas supprimer le chemin `runtimePayload` au profit d’une architecture non validée.

### Application générée

- Corriger l’émission d’intention ou l’application de payload.
- Retirer les stubs locaux du bridge host.
- Afficher une évolution utilisateur claire et continuer l’expérience après succès.

### IA runtime / prompt

- Renforcer les instructions de sortie si le payload est absent, non projetable ou trop analytique.
- Garder la réponse orientée application runtime, pas analyse générale.

## Entrées / sorties

### Entrées

- Diagnostic v1 actionnable.
- Contrat `creatia-runtime/v1` applicable.
- Code, prompt, document ou test responsable de l’écart.
- Reproduction ou trace de l’échec.

### Sorties

- Correction ciblée dans la couche responsable.
- Vérification de non-régression du flux runtime.
- Documentation ou test mis à jour si la règle devient durable.
- Résultat utilisateur récupérable en cas de nouvel échec.

## Erreurs

- **Réparation sans diagnostic** : risque de corriger le symptôme ; reprendre le protocole Diagnose v1.
- **Correction par stub local** : interdite, car elle masque le bridge Creatia et fausse la compatibilité.
- **Réparation cassante** : créer une nouvelle couche versionnée uniquement si un changement cassant est explicitement demandé et validé.
- **Suppression du payload runtime** : interdite sans remplacement démontré d’une fiabilité au moins équivalente.
- **Documentation oubliée** : si la réparation formalise une nouvelle règle, mettre à jour la gouvernance, les prompts, tests ou API runtime concernés.
